# 评审报告：Gemini UI 界面优化方案 v2.0 复审

评审对象：`docs/06-ui-optimization-proposal.md` v2.0 及 5 张新版设计稿
评审日期：2026-08-20
评审方式：逐条核对 Gemini 的问题关闭声明，并检查新增设计是否与需求、详细设计和当前代码一致。

## 1. 结论先行

结论：**本轮修正有效，但「已关闭全部 P1」的声明不成立；仍需关闭 6 个 P1 后再进入编码。**

可以认可的主要改进包括：生成中按钮改为「停止」、Esc 恢复为始终隐藏、双路状态分开、双模板恢复、模型名保持自由输入、历史列表压缩、设备徽章降级、AppDelegate 纳入 UI-1 文件范围。

仍然阻塞编码的问题集中在四类：设计稿实际比例与标称尺寸不一致、设置导航稿互相矛盾、局部重试新增业务语义未设计、方案中的实现分支仍以「或」保留而没有作出决定。此外，新增功能尚未写回项目规定的权威详细设计。

## 3. P1（必须修改，否则不应开工）

### P1-1：面板稿仍未按 560 × 600 的真实比例绘制

- [ ] **位置**：第 27 至 38、190 行；`lighttrans_panel_streaming.jpg`、`lighttrans_panel_partial_fail.jpg`。
- **问题**：目标宽高比为 560 / 600 ≈ 0.93；两张图中的窗口外框宽高比目测约为 0.72，仍比目标窗口窄约四分之一。失败稿与生成稿内部构图也不同：输入区标题、字体、双语标题、卡片高度和状态栏位置没有保持同一组件体系。
- **进一步证据**：文档指定的固定高度合计为 110 + 36 + 180 × 2 + 24 = 530 pt。再加上下各 16 pt 外边距和至少 4 个 10 pt 间距即达到 602 pt，尚未计入分隔线与其他间距，当前规格无法完整放进 600 pt。
- **建议修改**：用真实 560 × 600 比例的画板重新排版，并给出严格的垂直尺寸表。建议不要同时固定两张结果卡为 180 pt，可让结果区平分剩余高度。两张状态稿必须使用同一组件尺寸，仅改变内容和状态。

### P1-2：两张设置稿的导航结构互相矛盾，技术方案仍未作选择

- [ ] **位置**：第 55 至 66、145 至 151 行；两张设置稿。
- **问题**：接口稿与模板稿的侧边栏分类、图标、顺序和标题均不同。文档又写「Tab 真实分页导航（或侧边栏切换）」和「TabView 或精致侧边栏列表」，仍把两个不同实现留给编码阶段决定。
- **建议修改**：固定采用一种结构。推荐采用与设计稿一致的左侧分类列表，统一为「接口配置、提示词模板、通用与快捷键、历史记录」4 项；两张稿使用完全相同的侧边栏、窗口标题和选中样式。技术方案写明具体 SwiftUI 结构，不保留「或」。

### P1-3：局部重试改变任务与历史语义，当前方案没有定义

- [ ] **位置**：第 49、131、190 行；`PanelViewModel.swift` 第 39 至 66、104 至 143 行。
- **问题**：当前一次翻译由一个协调任务并行执行两路，两路结束后立即追加一条聚合历史记录。新增「只重试失败路」后，以下问题均未定义：
  1. 重试使用发起原翻译时的输入快照，还是输入框当前值；
  2. 是否清空失败路已经收到的部分结果；
  3. 第一次失败记录是否已经写入，重试成功后如何记录；
  4. 只追加历史禁止修改旧记录，是否追加第二条记录以及如何避免重复直译；
  5. 重试期间全局停止按钮、generation 和另一段结果如何处理；
  6. 哪些错误允许重试，鉴权失败和配置错误应改为打开设置而不是重复请求。
- **建议修改**：最低成本方案是本轮删除局部重试，只提供全局「重新翻译」并沿用现有协调与历史语义。若必须保留局部重试，先在详细设计中完整定义上述状态机、历史策略和验收用例，再修改代码。

### P1-4：设置与历史直达的调用方式仍未确定，直接调用当前不可行

- [ ] **位置**：第 135 至 139 行；`AppDelegate.swift` 第 106 至 140 行。
- **问题**：文档保留 NotificationCenter 与直接访问 AppDelegate 两种方案。当前两个打开方法是 private，`TranslatePanelView` 或 `PanelViewModel` 无法直接调用；把 UI 直接绑定到 `NSApp.delegate` 还会增加不必要耦合。
- **建议修改**：推荐由 `TranslatePanelView` 接收 `onOpenSettings`、`onOpenHistory` 两个闭包，AppDelegate 创建 root view 时注入；或固定采用两个明确命名的 Notification。二选一写进方案，不在编码时临时决定。

### P1-5：搜索选择清理只覆盖「零结果」，没有覆盖选中项被过滤

- [ ] **位置**：第 100 至 101、174 至 176 行；`HistoryWindowView.swift` 第 12 至 23 行。
- **问题**：如果筛选后仍有匹配记录，但当前选中记录不在结果中，文档没有说明选择哪条记录。当前 `selectedRecord` 仍从全部 `records` 中查找，右侧会继续展示已从左侧消失的旧记录。
- **建议修改**：`selectedRecord` 必须从 `filtered` 中解析。筛选变化后：当前选择仍在结果中则保留；否则有结果时选择第一条；无结果时置 nil。刷新数据后使用同一规则。

### P1-6：新增功能尚未写回权威详细设计，不能按项目规则直接编码

- [ ] **位置**：第 14、49、71 至 74、131、153 至 159、186 至 192 行；`docs/03-detailed-design.md` 第 437 至 464 行。
- **问题**：局部重试、连接测试、设置分页和面板直达窗口均为详细设计未覆盖的新行为。项目规则明确规定实现细节以 `docs/03-detailed-design.md` 为准，未覆盖的决策不得在代码中即兴决定。文档第 14 行声称业务和存储契约不变，但局部重试会直接影响任务状态与历史写入语义。
- **建议修改**：UI 方案评审通过后，把最终确定的交互和状态机写回 `docs/03-detailed-design.md`，并在 `docs/04-implementation-plan.md` 增加 UI-1 至 UI-3 的执行顺序、验证项和确认门槛。完成文档评审后再编码。

## 4. P2（应当修改）

### P2-1：长设备名与模型名不能承诺永不截断

- [ ] **位置**：第 94 至 96、192 行。
- **问题**：两个字符串长度没有上限，410 pt 无法保证同时完整显示。设计稿中的短示例不能证明长文本安全。
- **建议修改**：第二行使用两列 Grid 并定义最小宽度、layoutPriority、单行中间截断和 hover 提示；或改为设备、模型各占一行。验收使用至少 30 个字符的设备名和模型名。

### P2-2：失败稿的警告区域过重且存在占位文案

- [ ] `lighttrans_panel_partial_fail.jpg` 使用大面积黄褐色背景，并显示英文占位文案「Warning state」。该区域视觉权重高于成功结果，却没有提供真实错误信息。建议改为卡片内紧凑错误说明、错误图标与「重试／检查设置」动作，不使用大面积警示底色。

### P2-3：「停止」按钮的红色权重仍偏高

- [ ] 停止翻译可恢复且会保留部分结果，不属于不可逆危险操作。建议保持按钮位置和尺寸，使用系统按钮样式、`stop.fill` 和轻量红色 tint；避免高饱和红底成为面板最强视觉元素。

### P2-4：图标与界面语言仍不统一

- [ ] 失败面板使用「Direct Translation / 直译」「Prompt Rewrite / 转写」和彩色字符，生成面板只用中文与单色图标；模板页也仍有彩色书本、星光字符。统一为中文标题与 SF Symbols template rendering。

### P2-5：浅色与关键空状态稿仍缺失

- [ ] 本轮补了生成和单路失败，但仍没有面板空闲、设置测试失败、历史无结果、浅色关键界面。至少补面板空闲浅色稿和历史无结果稿；其余状态可用标注线框说明。

### P2-6：测试连接需要明确费用和成功边界

- [ ] `max_tokens: 5` 仍会向真实模型发起请求并可能产生费用。设置页说明应明确「会发送一个最小测试请求，可能产生极少量费用」；成功文案只表示本次请求成功，不代表所有提示词和长输出一定可用。

### P2-7：材质选择仍然不确定

- [ ] 第 38、110 行继续使用 `.ultraThinMaterial / NSVisualEffectView` 和 `.hudWindow 或 .popover`。Apple 建议按用途选择材质，不能按最终颜色临时挑选。方案需固定实现方式和材质，并补充 Reduce Transparency、Increase Contrast 的验收。

### P2-8：设置模板稿仍使用等宽字体，与文字规范不一致

- [ ] 第 78 行写「系统文本排版」，模板设计稿却明显使用等宽字体。提示词主要是自然语言，建议正文使用系统正文或编辑器字体，只对 `{{text}}` 示例和校验徽章使用等宽字体。

### P2-9：列表状态不能只靠颜色表达

- [ ] 历史列表仍以绿、橙、红圆点作为唯一状态标识。应为图标提供 `accessibilityLabel`，并在选中行或 hover 帮助中提供「完成／已停止／失败」文字；颜色只作为辅助。

## 5. P3（建议优化）

### P3-1：统一字符统计格式

- [ ] 两张面板稿统一使用「82 个字符」或紧凑的「82 字符」，不要混用「436 / 字」。

### P3-2：统一窗口标题和设置分类

- [ ] 接口稿标题为「LightTrans设置」，模板稿为「设置」；统一为「轻译设置」或「设置」。两张稿的分类名称、顺序、图标和侧边栏宽度必须完全一致。

### P3-3：设计稿使用真实可读示例文本

- [ ] 历史稿和模板稿存在语义不通的占位文本，不利于判断换行、选择和长文本阅读效果。使用项目默认提示词和一组真实中英文翻译示例。

### P3-4：补充精确尺寸标注

- [ ] 历史稿已有 270 / 410 / 480 pt 标注；面板与两张设置稿也应标出窗口外框和主要区域尺寸，并保证导出画板宽高比与标称尺寸一致。

## 6. 最终判断

| 界面 | 当前判断 |
| --- | --- |
| 浮动翻译面板 | 状态表达改善明显，但真实尺寸和局部重试语义仍阻塞实现 |
| 设置窗口 | 字段页本身可用，但导航系统不一致，尚不能作为统一实现依据 |
| 历史记录窗口 | 本轮完成度最高；补齐选择规则、长文本策略和无颜色状态说明后可进入实现 |

总体结论：**修改 P1 后通过。** 不需要推翻当前视觉方向；优先修正尺寸、统一设置导航、删除或完整设计局部重试，再把最终决定写回详细设计与实施计划。
