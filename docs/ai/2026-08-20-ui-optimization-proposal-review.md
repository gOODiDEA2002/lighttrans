# 评审报告：Gemini UI 界面优化方案

评审对象：`docs/06-ui-optimization-proposal.md` v1.0
评审日期：2026-08-20
评审范围：用户体验、UI 美观度；同时核对方案与现有需求、详细设计和代码是否一致。

## 1. 结论先行

结论：**修改 P1 后复审，当前不建议直接进入编码。**

方案方向基本正确：浮动面板使用系统材质、补充空状态、强化复制反馈、增加设置与历史入口，这些改动能改善现有界面的完成度。问题在于，当前文档更像「功能与视觉想法清单」，还不是可执行、可验收的 UI 设计：没有线框图或视觉稿，没有关键状态矩阵，多处交互与已确认需求冲突，且「测试连接」已经超出纯 UI 优化范围。

基于文字方案的审查性评分如下。由于没有视觉稿，UI 美观度评分仅代表设计方向，不代表最终效果。

| 维度 | 评分 | 判断 |
| --- | ---: | --- |
| 用户体验方向 | 6 / 10 | 高频入口、空状态、复制反馈有价值，但 Esc、错误恢复、搜索选择和连接测试尚未定义清楚 |
| UI 美观方向 | 6 / 10 | 材质、语义色和弱化描边方向合理，但存在「卡片过多、动画过多、装饰先于信息层级」的风险 |
| 设计交付成熟度 | 3 / 10 | 缺少视觉稿、状态稿、尺寸与样式规则，验收条件多为主观形容词 |

## 2. 已确认的优点

1. 浮动面板从纯描边改为系统材质与弱背景，符合轻量悬浮工具的定位。
2. 增加空状态、复制成功反馈、设置与历史直达入口，能降低首次使用和重复操作成本。
3. 直译与转写使用不同标题和图标，有助于快速识别两种结果。
4. 历史记录增加无结果提示和结果计数，能修复当前搜索后只显示空白列表的问题。
5. 保持系统语义色和原生组件、不引入第三方依赖，符合项目的轻量与兼容性约束。

## 3. P1（必须修改，否则不应开工）

### P1-1：缺少视觉稿和完整状态稿，无法评审或验收「美观」

- [ ] **位置**：第 3 节、第 4 节全部验收标准。
- **问题**：文档只描述「精致毛玻璃」「轻微高光」「微弱骨架线」「平滑动效」等方向，没有界面构图、信息层级、间距、字体、控件尺寸和状态切换稿。「`.hudWindow` 或 `.popover`」也没有作出选择。同一段描述可实现出差异很大的界面。
- **依据**：第 78 行把「具备精致毛玻璃质感」作为验收标准，但该表述不可测量，也无法支持浅色、深色和不同壁纸之间的一致比较。Apple 也要求按语义用途选择材质，而不是按材质呈现出的颜色选择，并要求在不同上下文中验证可读性。
- **建议修改**：编码前新增一个 UI 设计附件，至少包含：
  1. 翻译面板的空闲、已输入、双路生成、单路失败、全部完成、已复制 6 个状态；
  2. 设置窗口的默认、API Key 显示、连接测试中、成功、失败 5 个状态；
  3. 历史窗口的有记录、无记录、搜索无结果、存在 iCloud 待下载记录 4 个状态；
  4. 浅色与深色各一套关键状态图；
  5. 统一的间距、圆角、字体、语义色、材质、描边和动画时长表；
  6. 固定选择一种面板材质，并说明选择理由。

### P1-2：Esc 改为「先清空、再隐藏」违反已确认需求，并引入误清空风险

- [ ] **位置**：第 47 行。
- **问题**：方案把 Esc 从「隐藏面板」改成第一次清空输入、第二次隐藏，改变了已形成的快捷键习惯，并可能在用户只想关闭面板时误删尚未翻译的输入。清空输入后是否同时清空两段结果和状态也没有定义，容易出现「空输入对应旧结果」的界面错配。
- **依据**：`docs/01-requirements.md` 第 27 行与 `docs/03-detailed-design.md` 第 195 行都明确规定 Esc 隐藏面板；当前 `FloatingPanel.cancelOperation` 也直接隐藏窗口。方案第 14、21 行又声明业务逻辑完全不变，前后矛盾。
- **建议修改**：保持 Esc 单次隐藏不变。一键清空只通过明确按钮触发，并定义清空范围。推荐将其定义为「重置本次内容」：非翻译中时同时清空输入、两段结果和状态；翻译中时先停止或禁用该按钮。按钮需要 `help` 或可访问性标签说明影响范围。

### P1-3：「测试连接」不是纯 UI 优化，行为、费用和错误口径尚未设计

- [ ] **位置**：第 30、79 行。
- **问题**：测试 Base URL、API Key 和模型是否可用必须真实发起网络请求，属于新增业务能力。方案未定义请求内容、是否消耗额度、使用编辑中还是已保存的 API Key、超时与取消、是否写历史、如何区分鉴权成功但模型无权限等情况，也没有说明是否复用当前流式翻译接口。
- **依据**：现有 `TranslationService` 只有带实际模板与正文的翻译入口；设置页的 UserDefaults 项即时保存，但 API Key 在失焦或窗口关闭时才写入钥匙串。直接实现会产生「点击测试时究竟测试哪个值」的歧义。
- **建议修改**：如果保留该能力，先更新需求与详细设计，再单独列为功能任务，不放在纯视觉任务中。设计至少明确：
  1. 使用设置页当前内存中的 Base URL、模型与 API Key，不要求先保存；
  2. 发送不含用户正文和提示词的最小请求，明确可能产生极少量费用；
  3. 不写历史记录，支持取消，设置明确超时；
  4. 区分地址错误、网络错误、鉴权失败、模型不存在或无权限、限流和额度不足；
  5. 成功仅表示当前配置完成了一次最小请求，不宣称所有翻译能力都可用。

### P1-4：面板内打开设置与历史的实施文件不完整

- [ ] **位置**：第 67 至 70 行、第 78 行。
- **问题**：UI-1 只列出 `FloatingPanel.swift`、`TranslatePanelView.swift` 和 `PanelViewModel.swift`，但设置与历史窗口由 `AppDelegate` 管理，现有 `openSettings`、`openHistory` 还是私有方法。当前文件列表无法完成验收标准。
- **依据**：`Sources/LightTrans/AppDelegate.swift` 第 106 至 140 行负责创建、激活和显示两个窗口；翻译面板当前没有相应回调或环境动作。
- **建议修改**：把 `AppDelegate.swift` 加入 UI-1，设计明确的动作注入方式，例如由 `TranslatePanelView` 接收 `onOpenSettings` 和 `onOpenHistory` 闭包。验收时验证：点击入口后翻译面板自动隐藏、目标窗口正确激活并聚焦、再次呼出面板仍保留内容。

### P1-5：错误恢复流程没有落到详细方案

- [ ] **位置**：第 20、55、78 行。
- **问题**：设计原则声明要提供「更聚焦的警示文案与容错引导」，详细方案却只设计了生成中状态，没有说明失败信息放在哪里、长错误如何显示、部分成功如何处理、下一步操作是什么。
- **依据**：当前 `ResultSection` 将失败文案限制为一行，长错误会被截断；双路请求可能出现一段成功、一段失败。现有问题没有被方案覆盖。
- **建议修改**：补充双路状态矩阵：
  - 未配置：在对应结果区显示简短说明，并提供「打开设置」动作；
  - 网络、限流、额度、地址错误：显示可完整阅读的摘要和「重试」或「检查设置」动作；
  - 单路失败：保留另一段成功结果与复制能力，不用全局错误覆盖；
  - 长错误：允许换行或通过详情展开，不使用单行截断作为唯一信息；
  - 所有状态同时提供文字与图标，不只依赖红色。

### P1-6：历史搜索会出现「列表无结果，但右侧仍显示旧记录」的错配，方案未覆盖

- [ ] **位置**：第 31、80 行。
- **问题**：方案只增加搜索空状态，没有定义筛选后选中项的处理。当前代码从全部 `records` 中解析 `selectedRecord`，而不是从 `filtered` 中解析；选中一条记录后输入不匹配的关键词，左侧会为空，右侧仍显示旧记录。若加上空状态提示，矛盾会更明显。
- **依据**：`HistoryWindowView.filtered` 位于第 12 至 19 行，`selectedRecord` 位于第 21 至 23 行，二者使用的数据集合不同。
- **建议修改**：筛选条件变化后，如果当前选中项不在筛选结果中，则选择第一条匹配记录；没有匹配项时清空选择并显示专用空状态。首次打开和刷新后也要定义默认选择行为。空状态至少区分「暂无历史记录」「没有匹配结果」「记录待从 iCloud 下载」。

## 4. P2（应当修改）

### P2-1：材质与卡片叠加过多，可能从「轻量」变成「卡片堆叠」

- [ ] **位置**：第 18、40 至 44、58 至 60、80 行。
- **问题**：窗口毛玻璃、输入卡片、两段结果卡片、转写高光边框、历史详情卡片同时叠加，容易形成多层圆角容器，信息层级反而变弱。`controlBackgroundColor` 的语义是较大的控制或内容背景，叠加 `opacity(0.7)` 后的实际对比度还会随壁纸和系统设置变化。
- **建议修改**：只保留两级表面：窗口材质为一级，输入与结果的弱背景为二级。结果区优先用标题、间距和细分隔线区分，避免每块都增加独立描边。转写与直译用图标和标题区分，不再额外增加彩色高光边框。

### P2-2：持续呼吸动画没有必要，优先使用系统进度指示

- [ ] **位置**：第 20、54 至 55 行。
- **问题**：翻译文本本身已经在流式变化，持续脉冲属于重复反馈，频繁使用时可能分散注意力。自定义动画还缺少「减少动态效果」适配。
- **建议修改**：首个片段到达前在每段标题旁使用小型 `ProgressView`；收到片段后保留简短状态文字或静态活动图标即可。复制成功只做一次短暂的 symbol replacement 或淡入淡出。检测系统 Reduce Motion，在开启时取消重复动画。Apple 建议动画应有明确目的，并优先使用小型系统活动指示器表达空间受限的异步任务。

### P2-3：「停止」使用大面积警示红色过重

- [ ] **位置**：第 51 至 53 行。
- **问题**：停止翻译是可恢复的取消动作，不是删除数据或不可逆危险操作。把整个主按钮改成警示红色会造成视觉跳变，也会让中断动作显得比翻译本身更危险。
- **建议修改**：保持按钮位置和尺寸不变，使用 `stop.fill` 图标、清晰的「停止」文字与系统控件样式；如果需要红色，只用于图标或轻量 tint。状态不能只靠颜色表达。

### P2-4：空闲状态不应使用骨架线

- [ ] **位置**：第 61 至 62 行。
- **问题**：骨架屏通常表示内容正在加载，在尚未发起翻译时显示会产生错误暗示。
- **建议修改**：空闲状态只使用一个低强调度图标、一句说明和快捷键提示；生成中才显示活动指示器。若输入为空，主按钮应禁用，避免点击后无反馈。

### P2-5：粘贴按钮与字符统计缺少明确价值，可能增加噪声

- [ ] **位置**：第 45 至 48 行。
- **问题**：输入框已自动聚焦，`⌘V` 是 macOS 标准操作；为了判断「剪贴板含文本」而持续读取剪贴板也没有必要。字符数在没有输入上限时不能帮助判断费用或可提交性，且「128 字」对英文、符号和表情并不准确。
- **建议修改**：如保留粘贴按钮，固定预留按钮位置，只在点击时读取剪贴板，避免按钮出现和消失导致布局跳动。字符统计在没有限制或费用提示前建议移除；如确有需要，使用「128 个字符」，并明确统计规则。

### P2-6：提示词全部改用等宽字体不利于长文本阅读

- [ ] **位置**：第 30、79 行。
- **问题**：直译和转写模板主要是自然语言，不是代码。等宽字体会降低同宽窗口中的信息密度，也不等于更专业。
- **建议修改**：模板正文继续使用系统正文或编辑器字体；把 `{{text}}` 校验状态做清楚即可。若需要代码感，只对占位符示例使用等宽字体。

### P2-7：API Key 明文切换需要定义安全与焦点行为

- [ ] **位置**：第 30、79 行。
- **问题**：该功能有实际排错价值，但方案没有说明默认状态、窗口重新打开后的状态、切换时是否丢焦点，以及如何避免长时间暴露密钥。
- **建议修改**：默认始终隐藏；窗口重新打开时恢复隐藏；显示按钮带「显示 API Key／隐藏 API Key」可访问性标签；切换只改变呈现，不改变内存值和钥匙串写入时机。可考虑按住显示而不是锁定显示。

### P2-8：历史列表中的「设备胶囊」可能挤压核心信息

- [ ] **位置**：第 80 行。
- **问题**：当前列表宽度只有 240 至 340 pt，设备名可能很长。状态点、时间、设备胶囊和输入摘要同时放入列表项，会产生拥挤和大量截断。
- **建议修改**：列表项以输入摘要为第一视觉层级；时间与设备放在次级行，设备使用普通次要文本并截断。状态使用有含义的图标加文字或可访问性标签，不只使用彩色圆点。胶囊只在确有筛选或操作价值时使用。

### P2-9：固定 560 × 600 面板继续增加内容，缺少小屏与内容压缩策略

- [ ] **位置**：第 67 至 70、78 行。
- **问题**：现有面板已经固定为 560 × 600；增加底栏、卡片内边距和标题图标后，只能压缩输入或两段结果。方案没有定义最小结果高度、窗口超出当前屏幕时的处理，也没有说明底栏是否值得永久占用空间。
- **建议修改**：先画出 560 × 600 的真实尺寸稿，明确输入区、操作区、两段结果和辅助入口的高度。设置与历史入口可放在紧凑的顶部或操作行，不一定单独增加 24 pt 底栏。验证低分辨率和缩放显示环境下窗口完整可见。

### P2-10：性能结论没有测量依据

- [ ] **位置**：第 91 至 92 行。
- **问题**：「CPU 占用几乎零增量」和「完全满足 NFR-2」是未验证断言。窗口材质会参与合成，重复动画也会在生成期间持续刷新。
- **建议修改**：改为待验证假设。记录改造前后的空闲内存、面板显示时内存、空闲 CPU、双路流式生成时 CPU，并验证 Reduce Transparency 和 Reduce Motion。NFR-2 只在实测空闲内存低于 100 MB 后判定通过。

## 5. P3（建议优化）

### P3-1：统一用户可见快捷键写法

- [ ] 把 `Cmd+Return`、`Cmd+Shift+1` 等技术写法改为 macOS 常用符号形式，如 `⌘↩`、`⇧⌘1`、`⇧⌘2`。按钮 `help`、辅助栏和文档使用同一套写法。

### P3-2：术语改为「流式生成」

- [ ] 第 20 行的「流式推理过程」与产品行为不符；界面只展示翻译或转写的流式输出，并不展示模型推理。建议改为「流式生成过程」。

### P3-3：明确描边单位

- [ ] 第 41 行使用「1px」，SwiftUI 和 AppKit 布局通常以 point 为单位。建议写为「0.5 pt 或 1 pt，以目标显示器实测为准」，避免在 Retina 显示器上产生预期差异。

### P3-4：核对 SF Symbols 的最低系统版本与可访问性

- [ ] 所有图标都要在 macOS 14 上核对可用性；纯图标按钮必须提供 `help`、`accessibilityLabel` 和稳定的可点击区域。复制快捷键在结果为空时应禁用。

## 6. 推荐的修订任务顺序

1. **UI-0：视觉与状态规格**。先完成关键界面稿、状态矩阵、样式规则和可访问性规则，不改代码。
2. **UI-1：浮动面板体验优化**。优先处理信息层级、空状态、错误恢复、复制反馈和设置／历史入口；Esc 行为保持不变。
3. **UI-2：历史窗口优化**。先修复筛选与选择错配，再做空状态、状态标识和详情层级。
4. **UI-3：设置窗口视觉优化**。优化分组、说明和 API Key 显示；模板正文不强制等宽。
5. **UX-1：连接测试功能**。作为单独功能变更补充需求与详细设计，通过评审后再实现。

## 7. 建议验收矩阵

| 维度 | 必测内容 |
| --- | --- |
| 外观 | 浅色、深色、不同壁纸、Increase Contrast、Reduce Transparency |
| 动效 | 默认、Reduce Motion；复制反馈和生成状态不能阻塞操作 |
| 键盘 | `⌥T`、`⌘↩`、Esc、复制快捷键、Tab 焦点顺序、Full Keyboard Access |
| 面板状态 | 空闲、输入、双路生成、单路失败、全部失败、停止、完成、复制成功 |
| 设置状态 | API Key 隐藏与显示、测试中、测试成功、各类失败、窗口关闭重开 |
| 历史状态 | 无记录、有记录、无匹配、切换筛选、刷新后选择、iCloud 待下载 |
| 性能 | 改造前后空闲内存、面板显示内存、空闲 CPU、双路生成 CPU |
