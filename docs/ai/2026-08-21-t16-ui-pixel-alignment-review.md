# 评审报告：T16 真机反馈与像素对齐返工

评审对象：当前 T15–T16 未提交实现、`docs/06-ui-optimization-proposal.md`、`docs/assets/`

评审日期：2026-08-21

## 1. 结论

T16 验收不通过，需要返工。

1. 输入高度手柄存在确定性交互缺陷：透明手柄区域把拖拽交给了可按背景移动的 `NSPanel`，窗口移动优先于输入高度调整。
2. 当前 UI 与设计资产存在明显视觉差异。
3. 现有资产不能直接作为唯一的逐像素基线：同一窗口的多张设计图在结构、文案、状态和交互上互相冲突，且 `docs/assets/README.md` 明确声明它们不是像素级验收基线。
4. 在继续视觉实现前，必须先产出一套无冲突的 v5 基准图和尺寸标注；否则 Cursor 仍需自行猜测，无法形成可重复验收。

## 2. P1

### P1-1：输入高度拖拽被窗口背景拖动截获

- **位置**：`Sources/LightTrans/UI/FloatingPanel.swift:17`；`Sources/LightTrans/UI/TranslatePanelView.swift:123`。
- **现状**：`FloatingPanel` 设置 `isMovableByWindowBackground = true`；手柄命中区是透明 SwiftUI `Rectangle`。
- **依据**：Apple 对 `isMovableByWindowBackground` 的定义是允许在窗口背景任意位置拖动窗口；透明 `NSView` 的 `mouseDownCanMoveWindow` 默认值为 `true`。这与当前现象一致。
- **修正方案**：保留面板其他背景区域可拖动，但把高度手柄改为 AppKit 事件视图，并重写 `mouseDownCanMoveWindow` 返回 `false`。该视图独立处理 `mouseDown`、`mouseDragged`、`mouseUp`、双击复位、Hover 光标和无障碍增减动作。
- **禁止方案**：不应全局关闭 `isMovableByWindowBackground`，否则会破坏详细设计规定的面板可拖动行为。
- **验收**：从 100 pt 向下拖至 240 pt 时，窗口原点保持不变；向上拖至 70 pt 时同样不移动；拖动面板其他背景区域仍可移动窗口。

### P1-2：当前不存在可执行的唯一像素基线

- **位置**：`docs/assets/README.md:3–14`、`docs/assets/`。
- **问题**：README 把图片定义为概念稿并明确排除像素级验收，但当前验收要求已变更为接近像素级对齐。
- **资产冲突**：
  1. `lighttrans_panel_mockup.jpg` 是 1200 × 896 横图，画面标注的 UI 却是 560 × 600 pt；`streaming` 和 `partial_fail` 是 896 × 1200 竖图。
  2. `panel_streaming` 有「Input」标题和等宽输入字体，`panel_mockup` 没有。
  3. `panel_partial_fail` 有局部「重试」按钮和中英双语标题，权威详细设计明确取消单路重试。
  4. 三张面板图都没有 T15 新增的高度拖拽手柄。
  5. 设置接口稿把成功状态放在测试按钮右侧；v4 规范和当前实现把状态放在按钮下方。
  6. 历史稿把搜索框和匹配计数分为上下两行，当前实现把搜索、计数和刷新压在同一行。
  7. 历史稿使用带「复制」文字的按钮，v4 规范和当前实现使用纯图标按钮。
- **影响**：选择不同图片会得到相互排斥的实现，无法用截图差分判断通过或失败。
- **修正方案**：新增 v5 唯一基准图；旧图移动到 `docs/assets/archive/` 或明确标记为历史参考，不再参与验收。

### P1-3：设置与历史窗口的 520 × 450、680 × 480 尺寸语义可能错误

- **位置**：`Sources/LightTrans/AppDelegate.swift` 的 `openSettings()`、`openHistory()`；`SettingsView.swift:49–57`；`HistoryWindowView.swift:24–47`。
- **问题**：设计稿的尺寸箭头覆盖完整窗口和标题栏；代码使用 `contentRect` 创建窗口，并让 SwiftUI 内容再次固定为 520 × 450 或最小 680 × 480。标准标题栏会额外增加窗口外框高度，真实 frame 大于设计稿标注。
- **附加问题**：设置页的 140 pt 侧栏、`Divider` 和 380 pt 内容区合计超过 520 pt。
- **修正方案**：v5 基准必须明确尺寸指完整 window frame。设置目标 frame 为 520 × 450 pt，历史目标 frame 为 680 × 480 pt；内容高度由 AppKit 根据标题栏反算。分栏宽度必须把 1 pt 分隔线计入总宽。
- **验收**：通过 `window.frame.size` 和截图同时确认，不再只检查 SwiftUI 根视图的 `.frame()`。

### P1-4：缺少截图基线和自动差分，无法证明像素对齐

- **问题**：当前只有 AI 生成的带背景、阴影和标注的 JPG，没有裁切后的窗口基准图，也没有稳定状态数据和截图命令。
- **修正方案**：
  1. 为 Debug 构建增加只用于验收的 UI Snapshot 模式，不进入 Release 行为路径。
  2. 固定面板 idle、streaming、done、partial-fail、stopped；设置 API、模板；历史正常、无结果、空记录等状态数据。
  3. 在目标 macOS 15.7.4、2× scale 下生成真实窗口 PNG。
  4. 对窗口 frame、分栏、卡片、内边距和控件位置做 1 pt 级几何检查；对最终 v5 PNG 做叠加差分。

## 4. 推荐返工路径

### WP-1：立即修复拖拽竞争

只修改高度手柄事件处理和必要文档，不改视觉基线。完成后真机验证窗口原点不变。

### WP-2：冻结 v5 视觉基线

以现有设计稿的整体气质和布局为输入，解决以下冲突后重制基准：

1. 保留统一任务语义，不增加单路重试。
2. 纳入高度拖拽手柄。
3. 设置成功状态同行、长错误换到下一行。
4. 历史保留刷新能力，但在基准图中明确位置。
5. 明确窗口尺寸指完整 frame。
6. 输出不带外部背景、尺寸箭头和宣传效果的 2× PNG。

### WP-3：Cursor 按 token 表重构

先把每个窗口的尺寸、间距、字号、圆角、描边、背景透明度、按钮高度和图标尺寸写成常量表，再实现视图。不得凭肉眼临时调整。

### WP-4：Codex 独立验收

1. 代码和文档一致性审查。
2. Debug、Release、签名验证。
3. 真实窗口 frame 测量。
4. 每个基准状态截图叠加对比。
5. 真机拖拽、键盘、Hover、深浅色和 VoiceOver 检查。

## 5. 开工判断

- WP-1 根因与方案已确定，可以立即实施。
- WP-2 至 WP-4 需要先确认是否采用「重制无冲突 v5 基准图，再做像素对齐」方案。
- 在 v5 基准确认前，不应继续大范围调整 SwiftUI 样式。
